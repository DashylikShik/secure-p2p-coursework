# Этап 2, часть 4: join, self-lookup, refresh и PING при переполнении k-bucket

**Задача:** показать самостоятельное присоединение к DHT и обслуживание ограниченной таблицы маршрутизации без полного реестра узлов. Код работает только на `127.0.0.1`. **Это не TLS, не готовый защищённый протокол и не 12-узловой стенд.**

## Что было до этого

В `dht_network.py` уже существовали подписанные `PING/PONG`, `FIND_NODE`, итеративный lookup, `RoutingTable` и вызов реального TCP `PING` при переполнении bucket. В этой части добавлены воспроизводимые сценарии и обслуживание.

## Новые методы `DHTNode`

- `join(bootstrap_peers)` — получает **только seed-адреса**, делает подписанный PING и затем `lookup_node(own_node_id)` для сбора контактов. `found=False` для собственного ID в self-lookup не является ошибкой: задача — расширить таблицу маршрутизации. Возвращает число контактов и список RPC/ошибок.
- `refresh_once(bucket_limit=2)` — выбирает непустые bucket по очереди, генерирует случайную 256-битную цель внутри соответствующего XOR-диапазона и выполняет обычный `lookup_node`. Не использует глобальный список адресов.
- `start_periodic_refresh(interval_seconds=60, bucket_limit=2)` — запускает отдельный поток, регулярно выполняющий `refresh_once()`; `stop_periodic_refresh()` останавливает его. Интервал должен быть положительным, значения задаются параметрами, не правкой исходного кода.
- `probe_history()` — показывает события проверки контактов: номер bucket, какой старый контакт проверяли, был ли живым и сохранился он или был заменён. **Ключи не пишутся в журнал.**

### Почему проверка LRU проводится вне блокировки

В предыдущем пилоте `_remember()` удерживал блокировку `self._lock` на время сетевого PING, что может создать взаимные ожидания между узлами. Теперь сначала снимок контактной таблицы берётся под блокировкой, PING выполняется **без неё**, а результат применяется только после повторной проверки, что старейший контакт не изменился. Если изменился — делается новая попытка, без опасного вытеснения чужого контакта.

## Запуск в CMD

Из корневой папки проекта, где `node.py`:

```bat
cd /d "C:\Users\Пользователь\Desktop\p2p_stage1\p2p_stage1"
py -m pip install -r requirements.txt
py -m unittest discover -s tests -v
py -m scripts.dht_demo
py -m scripts.dht_maintenance_demo
```

Ожидаемый итог тестов: **50 tests / OK** (42 прежних + 8 новых). В демонстрации появятся:

```text
2) Lookup E after join: found = True
4) Periodic refresh completed: 1
    live oldest: True -> kept_old
    dead oldest: False -> replaced
SUCCESS: join, manual+periodic refresh, live/dead LRU PING.
```

Число контактов, RPC, длительности и номера bucket могут отличаться от показанных примеров: это нормально, потому что ключи и расписание потоков не одинаковы.

## Файлы результатов

Новый JSON: `results\dht_maintenance_ГГГГММДД_ЧЧММСС_....json`.

Поля:

- `join` — сколько seed-адресов удалось опросить и контактов обнаружить.
- `lookup_e.found` — обнаружен ли E после присоединения A.
- `refresh_once.buckets` — сгенерированные цели поиска и номера bucket.
- `periodic_refresh_runs` — количество фоновых запусков в эксперименте.
- `lru_ping.live`, `lru_ping.dead` — зафиксированные PING-проверки двух состояний.
- `routing_after` — неполные локальные списки контактов каждого из пяти узлов.

`results/` исключена из Git. Сохраняйте первичные JSON отдельно для экспериментальной части работы.

## Ограничения и что осталось

Это пока пилот на пяти узлах, работающих в **одном Python-процессе**, а не независимые процессы. Есть discovery для непустых bucket, но нет полного сценария заполнения и старения всех 256 buckets, и ещё нет сравнительных `star`/`ring` bootstrap-прогонов. Отсутствуют подписанные DHT-записи `STORE/FIND_VALUE`, TLS 1.3, end-to-end защищённый туннель. Они будут реализовываться отдельно.

Также важно: `PING` проверяет живость контакта в момент проверки, но сам по себе не доказывает, что сеть устойчива ко всем отказам и атакам.
