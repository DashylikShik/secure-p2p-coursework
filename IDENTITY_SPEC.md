# Идентичность узла (этап 2, часть 2)

- Алгоритм долговременной идентичности: **Ed25519** через библиотеку `cryptography`.
- Каноническое кодирование `canonical_encode(identity_public_key)` = **32 raw-байта** Ed25519 public key (без PEM/hex/пробелов/префикса).
- `NodeID = SHA-256(canonical_encode(identity_public_key))`, результат — 32 байта (256 бит).
- При первом запуске создаётся уникальная ключевая пара; повторный запуск из того же каталога состояния загружает **тот же** закрытый ключ.
- Каталог состояния отдельный для каждого узла, по умолчанию `%LOCALAPPDATA%\secure_p2p_coursework\node_a` и `node_b`. Эти каталоги находятся **вне** репозитория.
- Закрытый ключ хранится в `identity.pem`, в учебном прототипе без пароля в формате PEM/PKCS8. Файл нельзя публиковать, включать в Docker image или передавать по сети. Защита файла зависит от прав учётной записи ОС; это не production-хранилище ключей.
- При повреждённом файле ключ **не создаётся заново автоматически**. Программа выдаёт ошибку, чтобы не изменить идентичность незаметно.
- При получении чужого контакта необходимо проверить `NodeID` по открытому ключу. **Один только правильно вычисленный NodeID не удостоверяет удалённый узел**: для защищённого обмена требуется проверить владение закрытым ключом в аутентифицированном handshake (этап 4).
- В этом подэтапе `identity.py` **не подключён к `node.py` и `RoutingTable`**. Интеграция с реальным PING/FIND_NODE предстоит дальше.

## Команды Windows CMD

```bat
py -m pip install -r requirements.txt
py -m unittest discover -s tests -v
py -m scripts.identity_demo --name A
py -m scripts.identity_demo --name A
py -m scripts.identity_demo --name B
```

Пример ожидаемого свойства: второй запуск A показывает тот же `NodeID` и `Existing identity loaded`, а B получает другой `NodeID`.
