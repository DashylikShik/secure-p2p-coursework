# Этап 2, часть 5: сравнение bootstrap-схем `star` и `ring`

Это **учебный пилот на пяти узлах**, выполняемый в одном процессе Python. Каждый узел имеет свой Ed25519 identity, сокет, порт, k-bucket и жизненный цикл. Адреса узлов известны **только тестовому оркестратору**. При присоединении `join` рабочему узлу передают исключительно **один seed-адрес**. Полного реестра `NodeID → адрес` внутри `DHTNode` нет.

## Важно: четыре разных понятия

- Underlay — действительная IP-достижимость. В пилоте все слушают `127.0.0.1` и физически работают на одном компьютере.
- Bootstrap-граф — **начальные знакомства**, прописанные в конфигурации.
- DHT-overlay — контакты, которые действительно появились в локальных `k-bucket` после join/lookup; они выводятся в JSON.
- Туннель — фиксированный путь прикладного сообщения через ретрансляторы; **не реализован** в этом эксперименте.

### Star (звезда)

`B → A`, `C → A`, `D → A`, `E → A`.

Каждый периферийный узел сначала знает адрес A. A не обладает каталогом участников до подключения остальных.

### Ring (кольцо)

`A → B`, `B → C`, `C → D`, `D → E`, `E → A`.

Каждый узел сначала знает адрес следующего. Это не означает запрет TCP между другими парами.

## Как запустить в Windows CMD

Из корня проекта:

```bat
py -m unittest discover -s tests -v
py -m scripts.bootstrap_compare --scheme both --runs 1
```

Ожидается `Ran 55 tests ... OK`. Для эксперимента — завершающая строка `SUCCESS: bootstrap pilot completed.`. Для большей наглядности:

```bat
py -m scripts.bootstrap_compare --scheme both --runs 3
```

Можно запускать схемы отдельно:

```bat
py -m scripts.bootstrap_compare --scheme star --runs 1
py -m scripts.bootstrap_compare --scheme ring --runs 1
```

Но для сравнительного эксперимента **рекомендуется `--scheme both`**: тогда обе схемы используют одинаковые `NodeID` и тестовые пары. `--runs` ограничен 1..10.

## Что записывает оркестратор

Под `results/bootstrap_compare_<timestamp>/` появляются:

- `star_run_01.json`, `ring_run_01.json` — полные сырые данные прогонов;
- `lookups.csv` — отдельная строка для каждого FIND_NODE: источник, цель, успешность, число RPC, итераций, длительность, ошибки;
- `summary.csv` — сводные показатели для каждой схемы и каждого прогона;
- `manifest.json` — настройки эксперимента и сведения об окружении.

`routing_before_lookup` и `routing_after_lookup` внутри JSON содержат **все локальные buckets** и число контактов. `joins` содержит результаты self-lookup при присоединении и длительность каждого join. `bootstrap_edges` в конфигурации — только схема начального подключения, не реальные маршруты данных.

Каждый запуск создаёт новый каталог, предыдущие не перезаписываются. `results/` исключена из Git, сырые результаты необходимо хранить отдельно для предъявления преподавателю.

## Как читать результаты честно

- `successes / count` — число успешных поисков среди тестовых пар. 20/20 означает успешную **пилотную** проверку, не 95% сходимости по полному экспериментальному протоколу.
- `unknown_before` — число случаев, когда у инициатора цель отсутствовала в таблице **непосредственно перед поиском**. Если оно равно нулю, этот прогон **не доказывает многопереходность** и **не выполняет условие 30 контрольных неизвестных целей**.
- `mean_join_ms` — средняя длительность join для присоединившихся узлов.
- `mean_contacts_after_join` — среднее число контактов после вступления.
- `mean_rpc` и `median_lookup_ms` — показатели поиска; время зависит от нагрузок компьютера.

**Ограничение:** при `N=5` после self-lookup каждый узел может узнать все остальные 4 адреса. Это допустимо для *пилота*, но является вырожденной таблицей для требуемого финального исследования. Строгая проверка невырожденности назначена для сети `N=12–15`, не менее 30 поисков неизвестных целей и как минимум 80% узлов с таблицами меньше `N-1`.

Эта часть **не создаёт TLS-сессию**: подпись RPC не скрывает содержимое сетевых кадров. `STORE/FIND_VALUE`, репликация и туннели будут реализованы позже.

## Как устроен код

- `configs/bootstrap_star.json` и `configs/bootstrap_ring.json` определяют фиксированные начальные знакомства, число узлов, k, alpha и timeout.
- `bootstrap_topologies.py` проверяет конфигурации, запускает узлы, по очереди вызывает `join`, снимает таблицы, запускает поиск и собирает показатели.
- `scripts/bootstrap_compare.py` предоставляет CLI для Windows, пишет CSV/JSON и краткий вывод.
- `tests/test_bootstrap_compare.py` автоматически проверяет схемы и три тестовых поиска для одинаковых NodeID в обеих топологиях.

Никакие существующие файлы первого и второго этапов, кроме `README.md`, менять не требуется. Личный конспект DOCX должен лежать **вне папки проекта**.
