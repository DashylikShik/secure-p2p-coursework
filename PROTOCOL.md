# Протокол сообщений (версия 1)

Каждый кадр состоит из фиксированного 24-байтового заголовка и JSON payload в UTF-8.

| Поле | Размер | Значение |
|---|---:|---|
| `version` | 1 байт | 1 |
| `type` | 1 байт | Код RPC |
| `flags` | 2 байта | 0 |
| `request_id` | 16 байт | Связь ответа с запросом |
| `payload_length` | 4 байта | Размер JSON в байтах, big-endian, не более 65536 |

Python: `struct.Struct('!BBH16sI')`. Типы: `PING=1`, `PONG=2`, `FIND_NODE_REQUEST=3`, `FIND_NODE_RESPONSE=4`, `STORE_REQUEST=5`, `STORE_RESPONSE=6`, `FIND_VALUE_REQUEST=7`, `FIND_VALUE_RESPONSE=8`, `ERROR=255` (зарезервирован).

TCP — поток байтов. `recv_exact()` собирает кадр из нескольких чтений, `read_frame()` проверяет ограничения до выделения буфера полезных данных. Один `recv()` нельзя считать одним кадром.

## Подписанный DHT RPC

Для DHT применяется подписанный JSON-конверт с полями `node_id`, `public_key`, `host`, `port`, `kind`, `request_id`, `body`, `signature`. Проверяется `NodeID = SHA-256(canonical_encode(public_key))`; подпись Ed25519 охватывает все поля конверта, кроме самой подписи. `request_id` также совпадает с полем заголовка кадра.

В **защищённом TLS-режиме** обязательны ещё два поля:

| Дополнительное поле | Формат | Назначение |
|---|---|---|
| `session_id` | 32 hex-символа (16 байт) | Случайный ID клиентской логической сессии |
| `message_id` | 32 hex-символа (16 байт) | Случайный ID действия, уникальный между TLS-сессиями |

Оба поля включаются в Ed25519-подпись. Ответ подписывает и возвращает те же `session_id` и `message_id`, клиент сравнивает их с ожидаемыми. TLS-сервер отклоняет конверт без этих полей, с повреждённой подписью или не соответствующий проверенному ключу TLS-клиента.

После проверки криптографической подлинности, **до исполнения RPC**, узел атомарно записывает ключ `(sender NodeID, message_id)` в `ReplayGuard`. Уже известный ключ не выполняется повторно ни в текущей TLS-сессии, ни в новой TLS-сессии одного работающего узла. При переполнении журнала сервер отклоняет новые запросы.

### Границы защиты

`ReplayGuard` хранит максимум 4096 идентификаторов в оперативной памяти в течение 3600 секунд и не переживает перезапуск узла. После истечения окна или перезапуска повторно подписанный старый запрос может быть принят снова. Это **ограниченная** прикладная anti-replay защита, не долговременная exactly-once гарантия. Сам TLS 1.3 также защищает записи канала от повторов в пределах TLS-соединения, но это отдельный механизм.

Legacy-демонстрации этапов 1–3 запускаются через простой TCP специально для учебной регрессии и не обладают указанными свойствами TLS. В новом TLS DHT-сценарии fallback на открытый TCP запрещён. Сквозное шифрование через туннель и итоговая проверка pcap выполняются отдельно.
